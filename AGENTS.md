# DiagnoseIt: agent and maintainer notes

Detailed behaviour notes for contributors and coding agents. Setup, commands, and layout are in
[`README.md`](README.md); this file covers how the pieces work and the rules they follow.

**Supported run path:** Docker Compose for API, web, database, Redis, and Celery. Expo runs on the host (`make expo-start`).

## Backend

### Django Apps

| App | Models |
|-----|--------|
| `users` | `User` (extended AbstractUser) |
| `medical_reports` | `MedicalReport`, `TestResult` |
| `prescriptions` | `Prescription`, `Medication` |
| `symptoms` | `Symptom`, `SymptomLog` |
| `diagnosis` | `Diagnosis`, `DiagnosisHistory`, `HealthTrend` |
| `lab_tests` | `LabTestType`, `LabTestUnit`, `UnitConversion` |

### API Endpoints

```
/api/auth/            register, login, profile, logout
/api/medical-reports/ CRUD, file upload, bulk upload, health trends (one test or several), async status polling
/api/prescriptions/   CRUD, file upload
/api/symptoms/        CRUD, logs, active symptoms
/api/diagnosis/       CRUD, AI generation
/api/lab-tests/       test catalog (list, add, change, remove), unit conversion
```

### Key Features

- **Authorization policy**: every feature is available to every signed-in user, including editing the shared lab catalog. Each user's own records stay private to them. Staff-only: the Django `/admin` (account management) and changing, testing, or resetting the shared AI service settings, which any signed-in user can read.
- **PDF Parsing**: Hybrid VLM (qwen3-vl:4b) + legacy regex. VLM runs async via Celery; uploads return immediately with `PENDING` status.
- **Async Architecture**: Redis broker; a Celery worker for parsing (`celery` queue) and a separate concurrency-1 worker for AI reviews (`ai_review` queue, `celery_review_worker`), so reviews reach the model server one at a time; 30 min task limit. A worker started without `-Q` only consumes `celery`, so reviews need the review worker running. Frontend polls `/api/medical-reports/reports/<id>/status/` every 5s from the report list and detail pages.
- **Unit Conversion**: Database-driven conversions between measurement units via REST API.
- **Lab Test Catalog**: `populate_lab_tests` loads tests, units, ranges, and aliases; `make migrate` and the self-hosted container startup run it after migrations. The catalog is also editable in the app (page `/lab-catalog`, `lab_tests/catalog.py`): it is shared by the whole server, and every signed-in user can add a test, change one, or remove one. An entry someone changes there is marked `edited_by_user` and `populate_lab_tests` then skips it, so an edit survives the next deploy; an entry added there is `source='user'`. Removing deletes an entry added in the app and deactivates a built-in one (the loader would restore a deleted one), and a deactivated entry is listed under `?active=false` and put back by setting `is_active`. Names and aliases are checked against the rest of the catalog first, since two tests answering to one name would match neither, and every change relinks every user's stored results; removing a test never deletes results, they go back to their printed name. Printed names are matched to catalog tests by `lab_tests/matching.py`, shared by the parsers, AI review, manual edits, and Health Trends: specimen and method notes, word order, and bracketed or comma-separated parts are ignored, while qualifiers such as urine, free, hs, direct/indirect, fasting, and ratio must agree, so different analytes never merge. Catalog aliases decide which variants merge; fasting, random, and post prandial glucose are separate tests. A clotting time, the laboratory's control run beside it, and their ratio are separate tests too (aPTT, aPTT Lupus Sensitive, aPTT Control, DRVV screen, its control, its ratio), since a control on the patient's trend would be wrong. A catalog name must not carry a comma before an antibody class ("Cardiolipin Antibody IgG", not "..., IgG"): a comma splits off a bare "IgG" reading, which would make the total immunoglobulin of that class match two tests and link to neither. `lab_tests/tests_catalog.py` pins the catalog test that names printed on real reports must reach. A result without a number ("Negative", "Absent") never links to a catalog test. Users can link printed names the catalog does not know to a catalog test (`lab_tests.UserTestAlias`, per user; the report review model suggests links on Health Trends and the user confirms each one); saving or removing a link relinks that user's results (`medical_reports/relinking.py`). After catalog or matching changes, run `manage.py relink_test_results` (a dry run) and then `--apply` to re-match stored results. Health Trends lists one entry per catalog test and puts values into the unit most results use, converting with the catalog's conversions for that test (`lab_tests/trend_units.py`); results in a unit that cannot be converted are listed but not plotted. A value must start with a number to link ("G1", "Positive (1.2)" stay unlinked). A row outside a known report section takes one from its unit (/hpf urine, % differential, cells per volume absolute), and user name links apply only where their test fits the section. The text parser ends a urine or blood count section at a blood panel heading ("LIVER & KIDNEY PANEL, SERUM"); `relink_test_results` recomputes each text-parser row's section from the stored report text, so parser fixes reach stored results without re-parsing. Unlinked spellings of one name ("Antibody, IgG", "ANTIBODY,IGG") share one Health Trends entry. Health Trends charts up to six tests together (`trends/multi/`, one series per test): clicking a test adds it to the chart and clicking it again removes it. The chart places every point by its report's date, so tests taken on different days line up (`src/utils/trendChart.ts`). Tests measured in one unit share an axis of real values; with different units each line is drawn over its own range as 0–100% and the page says so, or each test can be given its own panel. A single test is drawn exactly as before, with its reference range and status-coloured points. An antibody class (IgA, IgD, IgE, IgG, IgM) links to a total immunoglobulin only as the whole name; as one part of a longer name ("Herpes simplex virus 1+2, IgG") it never matches on its own. `/api/medical-reports/test-results/search/?q=` finds results by printed or catalog name with their reports (`?test=`, on both the Medical Reports and Health Trends pages; on Health Trends, Find beside an unlinked name searches there instead of leaving the page), and report detail responses include `neighbors` (previous and next report in the default list order). The Medical Reports page searches reports by name or lab and sorts them by report date, date added, or name; search, sort, and status filter live in the address (`q`, `sort`, `status`), and report pages move through the list as last shown there (`src/utils/reportList.ts`, per browser tab), falling back to `neighbors`. The sort is also remembered between visits (localStorage), so arriving with no `sort` in the address uses the one last chosen.
- **Prescriptions**: uploads take a clinic PDF or a photograph of the paper (`PRESCRIPTION_UPLOAD_EXTENSIONS`), return immediately at `PENDING`, and are read on the Celery worker exactly as a report is (`prescriptions/tasks.py`); the page polls `prescriptions/<id>/status/` every 5s and `prescriptions/<id>/reparse/` reads one again. `utils/prescription_parser.py` finds the text — a PDF's own text layer, or the report OCR model for a photo or a scan, with the image scaled to at most `PRESCRIPTION_OCR_MAX_EDGE` (1600px) on its longest edge and the reply held to `PRESCRIPTION_OCR_MAX_TOKENS` (1500), since a vision model charges by image area and one that starts repeating itself otherwise writes until it reaches the OCR setting's own limit — and the report review model reads the medicines out of it as JSON, since a prescription is prose rather than a table; with no model configured, or when the model returns nothing usable, the older pattern matching still runs, so an upload always produces something. A failure is kept on `parse_error` and shown on the card, naming the OCR server when that is what failed. What was read is editable: every medicine's name, dose, frequency, duration, and instructions can be corrected, one can be added, and one the model invented can be removed (`MedicationList`, `prescriptions/<id>/medications/`), because OCR on a handwritten or non-Latin prescription is a start rather than a record. "Chat with AI" on a card opens the chat beside the medicines, as the report page opens its pane beside the results. **AI review** checks the stored medicines against the prescription itself (`utils/prescription_review.py`, state in `prescriptions/ai_review.py` on `Prescription.ai_review`): it runs on the review worker's `ai_review` queue, one at a time, and sends the prescription's text plus, when the card's "Page images" checkbox is ticked, the original page as a picture. That box starts ticked for a photo or a scan, since checking OCR text against itself would confirm its errors rather than catch them, and unticked for a PDF whose own text layer was read; the choice is stored with the queued review (`ai_review.options`). It suggests corrections, medicines missed, and rows that are not medicines; unlike a report review **nothing is ever applied automatically**, because every change here is to a medicine. Each accepted change records what it replaced and can be undone, and a dismissed suggestion is remembered so a later review does not raise it again. The date on the upload form is typed or pasted as text (`DateTextInput`, `parseDateInput`), like the report form's. The list searches, sorts, and filters the way the Medical Reports list does: search covers the doctor, the clinic, the notes, and the medicines themselves (what someone remembers about a prescription is usually the medicine on it), sorting is by prescription date, date added, or doctor, and the status filter reuses `reportMatchesFilter`. All three live in the address (`q`, `sort`, `status`), and the sort is remembered between visits per list (`savedListSort`).
- **AI Diagnosis**: any OpenAI-compatible chat model (configured in AI settings or `OPENAI_*`) with JSON responses, anonymized data, graceful fallback without API key. The model is asked to work a differential rather than name one condition (`utils/llm_service.py`): up to five ranked explanations, each with its reasoning, what supports it, what argues against it, and the tests that would confirm or exclude it, plus the candidates it thinks are its own likeliest false alarms, patterns it noticed, cautions, and red flags. `normalize_diagnosis` trims that answer to a stored shape on `Diagnosis.analysis` and fills `condition_name`, `description`, and `confidence_score` from the leading candidate, so the list, the history, and the timeline sent to later diagnoses are unchanged. A differential does not fit in the 1000 tokens the service defaults to, so every diagnosis call asks for at least `DIAGNOSIS_REPLY_TOKENS`; a reply cut off mid-object parses as nothing at all.
- **Ask about a report**: `/api/medical-reports/reports/<id>/chat/` (GET the conversation, POST `{question}`, DELETE to clear) answers questions about one report from that report alone (`utils/ai_chat.py`, shared with prescriptions, which have the same pane behind "Ask AI" on each card; "Ask AI about this report" appears in the report page header once the report has results or text to discuss — not on `is_parsed`, which is set once at parse time and stays false for a report whose results the AI review or the user added afterwards — and opens the chat beside the results, in the same column the PDF compare pane uses, so only one of the two is open at a time). The AI diagnosis model answers, in prose rather than JSON (`ai_settings.client.chat_text`); the prompt carries the report's parsed results and its text, with the account holder's name, phone numbers, and emails replaced and boilerplate left out (`utils/report_redaction.py`), and the model is told to answer only from the report, to name no condition, and to send anything that matters to a doctor. The conversation is stored on `MedicalReport.ai_chat` (40 turns kept, the most recent 16 sent back as context), so follow-up questions work and it is still there on the next visit. A model failure returns 502 and stores nothing. The report page also exports or copies the report as JSON — its results and the text as printed, unredacted, since it is the user's own report going where they choose.
- **AI Settings**: `/api/ai-settings/` (page `/settings/ai`) configures the AI diagnosis, report OCR, and report review servers. Settings are shared by the whole server: any signed-in user can read them, but only staff can change, test, or reset them (`IsAdminUser`), since they decide where everyone's reports are sent and the connection test makes the server request a URL. The web page is read-only for other users. API keys are write-only, and `save_ai_config` drops a saved key when the provider or base URL changes, so a key is only ever sent to the server it was saved for. Each service has a temperature (blank uses the service default: diagnosis 0.3, OCR and report review 0.1). Report review can send PDF text, page images, or text with images only for scans.
- **AI Diagnosis Health Timeline**: the Generate dialog's "Health timeline" mode (`mode: timeline`, `period` 3m/6m/1y/2y/all, `summary`) sends the user's lab results, symptoms (began, updates, ended, or ongoing from before the period), prescriptions with medicines, and earlier AI assessments, grouped by date oldest first (`diagnosis/timeline.py`), with the user's own summary (saved as `User.health_summary`). The account holder's name, phone numbers, and emails are redacted; doctor names and report titles are left out. Past 60,000 characters the earliest dates are dropped and the prompt says so. `diagnoses/timeline-preview/` returns the exact prompt. A model failure returns 502 instead of saving a placeholder, and `Diagnosis.context` records the period and counts.
- **AI Review Privacy and Precision**: before a review request, `utils/report_redaction.py` replaces the patient's name (labelled name fields, titled names, the account holder's name), phone numbers, and emails with [REDACTED], and leaves out legal and contact boilerplate and headers repeated on later pages; lines results were read from are always sent. Page images black out the redacted words using the PDF text layer (scanned pages cannot be redacted). The model answers with a verdict, and `correct` stores no suggestions. Suggestions that only change capitals, spacing, or punctuation, rename a row to another name of the same catalog test, clear a status, or use a value not printed in the report text are dropped. Dismissed suggestions are remembered per report (`ai_review.dismissed`) and not shown by later reviews. A report page can ask one review to read the pages with the Report OCR model instead of the PDF text layer (`ocr`), and to send page images whatever the setting says (`images`); with both, each request carries the images and their OCR text. The choice is stored with the queued review (`ai_review.options`), and the stored `input_mode` is text, images, ocr, or images_ocr. Report OCR sends pages in batches of the OCR setting's "Pages at once" (`parallel_requests`, match the server's parallel slots), for both OCR parsing and OCR reviews (`utils.vlm_pdf_parser.read_pages`); pages render on the calling thread and requests reuse its loaded settings. Stored test names lose trailing separators such as "IgA -" or "Epithelial cells." (`lab_tests.services.tidy_test_name`).
- **AI Report Review**: A model configured in AI settings checks parsed results against the original PDF and suggests corrections, missing results, and rows to remove. Reviews run one at a time on the review worker, started from the report page, for several selected parsed reports from the reports list, or after parsing when chosen on the single or bulk upload form (the checkbox defaults to the automatic review switch in AI settings; each report costs one or more model calls). Suggestions change results when the user accepts them, or automatically for safe fixes when that is turned on: removing a row or correcting its unit, reference range, or status, only for rows whose own text line or page was sent to the model. Every applied change is recorded with the values it replaced and can be undone. Long reports are reviewed in overlapping parts (`utils/report_review.py`); review state lives on `MedicalReport.ai_review` (`medical_reports/ai_review.py`).
- **Validation**: `LabTestValidationRule` model for NORMAL/LOW/HIGH/CRITICAL classification. The catalog gives a test a reference range only when it does not depend on sex, age, the assay, or the time of day (so hemoglobin, ferritin, and hormones use the range printed on the report), and critical limits only for the tests in `populate_lab_tests.CRITICAL_LIMITS` (common adult panic values), converted into each alternate unit; a test added in the app has none. A row without a printed range is read against the rule for the unit it was printed in (`_status_from_db`).

## Docker Compose files

- `docker-compose.yml`: the self-hosted stack for local or remote servers. `DEBUG` is off; the web port is `DIAGNOSEIT_BIND:DIAGNOSEIT_PORT` (default `127.0.0.1:3000`), and the API is also bound to `127.0.0.1:8000` for existing reverse proxies. Nginx proxies `/api` and `/admin`. The backend's `docker/entrypoint.sh` generates a `SECRET_KEY` into the `app_data` volume when none is set, and with `DIAGNOSEIT_INIT=1` (backend only) runs migrations, `populate_lab_tests`, `collectstatic`, and optional superuser creation before the server starts. Workers wait for the backend to be healthy. The `ollama` profile adds a local OCR server. The database, media, and static volume names can be set in `.env` for older deployments.

The Makefile runs this same file. `make up` sets `DIAGNOSEIT_API_BIND=0.0.0.0` so the Expo app can reach the API on port 8000 (add the machine's LAN IP to `ALLOWED_HOSTS` in `.env`); the commented volume lines in the backend service enable live parser edits.

`environment:` entries override `env_file:`, so settings with a default in `docker-compose.yml` use `${VAR:-default}` interpolation. Set their production values in the server's `.env`.

## Production Deployment

Update code on the server, then run `docker compose up -d --build`. The backend migrates and loads the catalog on start. For a TLS proxy on the same host, leave `DIAGNOSEIT_BIND=127.0.0.1`, set `DIAGNOSEIT_PORT` to the port the proxy uses, and enable the HTTPS settings in `.env`.

Configure secrets first: copy `.env.example` to `.env` (gitignored) and set `SECRET_KEY`, `POSTGRES_PASSWORD`, `ALLOWED_HOSTS`, and the `VLM_*` OCR settings. Put an HTTPS reverse proxy in front that passes `X-Forwarded-Proto`. Existing installations that used the former production override must set `COMPOSE_PROJECT_NAME=diagnoseit`, `DIAGNOSEIT_DB_VOLUME=diagnoseit_postgres_data`, `DIAGNOSEIT_MEDIA_VOLUME=diagnoseit_media_data`, and `DIAGNOSEIT_STATIC_VOLUME=diagnoseit_static_data` in `.env` before starting the new stack. Keep the password accepted by the existing database; changing `POSTGRES_PASSWORD` does not change that database role's password. See `README.md` for the one-time static volume ownership step.

## Report formats

`utils/report_formats.py` lets layout-specific parsers run beside the generic text parser (`EnhancedMedicalPDFParser.parse_medical_report` calls `apply_report_formats`). Formats are loaded from `REPORT_FORMATS_DIR` (default `report_formats/`) and the modules in `REPORT_FORMATS`. For each report, the highest-priority `REPLACE` format that matches and returns rows supplies the results, and every matching `SUPPLEMENT` format adds rows that aren't already present; a format that raises is logged and skipped. Format rows go through `_build_numeric_result_row`, so they get catalog links and statuses like any other row. They carry `line_number=None`, so `relink_test_results` keeps their section rather than recomputing it from the text. The parse result lists the formats used in `report_formats`. Formats only see the text layer; OCR results are unaffected.

## Troubleshooting

**A deploy seems to change nothing in the browser:** `index.html` names the content-hashed bundles and is served `no-cache` (`frontend/diagnoseit-web/nginx.conf`); `/assets/` is immutable because a changed file gets a new name. A browser that cached `index.html` before that rule keeps loading the previous build, so hard-refresh once.

**Expo Go shows "Failed to download remote update":** the phone cannot reach Metro. Use `adb reverse tcp:8081 tcp:8081` and open `exp://127.0.0.1:8081` over USB, put the phone on the same network, or use an emulator on the host. Avoid `EXPO_HOST=tunnel` if everything should stay local; it relays through Expo's ngrok service.

```bash
lsof -i :8000; lsof -i :3000                       # port conflicts
docker compose logs -f db                          # database logs
docker compose logs -f celery_worker               # parsing worker
docker compose config                              # resolved settings (prints secrets)
```

OCR on CPU is slow (minutes per page); use a GPU-backed OCR server for real use.

## Mobile (DiagnoseItApp)

React Native + Expo SDK 57 app in `frontend/DiagnoseItApp/`, using the same **Specimen Ledger** theme (Literata + IBM Plex, paper/teal palette) as `diagnoseit-web`. On a device, `EXPO_PUBLIC_API_URL` must be an address the phone can reach, not `localhost`; the fallback is `app.json` → `extra.apiUrl`. Release builds (`make eas-android-apk`, `make eas-android-aab`) always run EAS `--local` and require an HTTPS API URL.

## Security

- Accounts: the first account registered on a server becomes staff and superuser; after that `/api/auth/register/` refuses new accounts unless `REGISTRATION_OPEN` is set, and `/api/auth/registration/` tells the apps whether to offer sign-up. Administrators add accounts in `/admin`.
- Login and sign-up are limited to 5 a minute per client. The client is the `X-Real-IP` the bundled nginx sets (`diagnoseit_backend/client_ip.py`); nginx takes it from `X-Forwarded-For` only when the connection comes from a private address, such as a TLS proxy on the host.
- `SECRET_KEY` is required when `DEBUG=False`; `ALLOWED_HOSTS` must list production domains.
- API authentication is token-only; tokens expire after `API_TOKEN_TTL_DAYS` and rotate on password change.
- CORS is open only in debug mode. Max upload size is 100 MB.
- Uploaded files are served through short-lived signed URLs.
- Names, phone numbers, and emails are redacted before text reaches an AI model.
